# 复杂页面数据驱动生成架构（ComplexPage Data-Driven Generation）

> 本文档供任何 AI（Codex / Claude / 其他）阅读后即可安全修改、扩展或实现相关代码。
> 它是复杂页面生成能力的**设计总纲**：先读本文档，再读
> `openspec/changes/complex-page-definition-and-binding/`（数据模型基础）与
> `openspec/changes/complex-page-container-ai-workflow/`（容器模型 + Agent 工作流）。
> 传统 CRUD 页面（`index/add/edit/detail`）的生成链路完全不受本文档影响。

---

## 1. 目标与问题

CodeMaster 现有代码生成以"一个实体 + 固定 pageType"为中心，擅长生成标准 CRUD。
但现实业务页面往往是**复杂页面**：

- 一个页面同时消费多个实体服务（主表 + 子表 + 关联字典）。
- 同一实体以集合（表格）和单体（表单/详情）两种形态同时出现。
- 页面有自定义布局（上方查询、下方主表、右侧详情），不是单实体模板能表达的。
- 页面展示需要字段级定制（某字段不显示控件，而显示自定义 HTML/模板）。

**方案核心一句话**：复杂页面 = 一棵**容器树**；每个容器（查询表单 / 编辑表单 / 表格 / 描述列表）
绑定一个**数据源**（服务契约 + 数据形态）；容器内的字段由**字段语义自动映射**出显示控件；
用户可以用**显示模板**覆盖任意容器或字段的渲染，全部定义存库、生成期输出 Vue。

设计约束：

- `tree.json` 是设计器与生成器的**唯一视觉事实源**，生成的 `.vue` 只是产物，禁止手工长期编辑。
- 定义（数据库）与产物（目标项目文件）分离；重新生成只更新受影响节点，保留用户布局与用户模板。
- 生成逻辑全部在 Application 层，Web / LocalAgent / Agent 共用同一契约。
- 不做像素级画布、不做任意 SQL 数据源、不做 Vue Script AST 反向解析。

### 1.1 当前模块边界

复杂页能力已全部并入独立项目，不再作为可剥离的插件存在：

- `CodeMaster.UiComposition`：核心定义、生成与 API。
- `CodeMaster.Agent`：结构化规划与审批适配（原 `UiComposition.Agent`，位于 `Tools/` 下）。
- `CodeMaster.LocalAgent`：本地元数据与生成包（原 `UiComposition.LocalAgent`，位于 `Extensibility/` 下）。
- `CodeMaster.McpServer`：MCP 工具（原 `UiComposition.McpServer`，位于 `Tools/` 下）。
- `CodeMaster.Migrator`：表结构迁移与种子（原 `UiComposition.Migrator`，位于 `Persistence/UiComposition/` 下）。

扩展通过 `ICodeMasterExtension` 在启动时扫描注册；宿主项目与自身程序集都在扫描范围内，
不再依赖复制 DLL 到 `modules/` 目录。

## 2. 核心概念模型

```
复杂页面
 └── 布局树（tree.json，视觉结构）
      └── 容器（container）：query-form | edit-form | table | description
           ├── 数据源绑定（dataSourceId）：service + method + dto + cardinality + parameters
           └── 字段条目（field）：由字段语义自动映射显示控件
                └── 可选覆盖：显示模板（容器级 items/item、字段级 row.field）
```

### 2.1 四类容器（构建复杂页面的唯一积木）

| 容器 | 作用 | 是否含 el-col | 渲染为 |
|------|------|---------------|--------|
| `query-form` | 查询条件区，通常位于页面上方 | 否（控件直接铺满一行，`el-form` inline） | `el-form` |
| `edit-form` | 新增/编辑表单 | 是（字段按栅格排布） | `el-form + el-row/el-col` |
| `table` | 集合/分页集合展示 | 是（表头按列排布） | `el-table` |
| `description` | 单体详情展示 | 是（条目按栅格排布） | `el-descriptions` |

**为什么只有四种**：这四种覆盖了 95% 以上业务界面（查、改、列、详情）。
超出范围的（图表、工作流、画布）属于特殊组件，用"显示模板覆盖"逃生，
而不是无限增加容器类型——容器类型越少，映射规则越简单，AI 越容易生成正确结果。

### 2.2 字段语义 → 显示控件自动映射

容器绑定数据源后，字段**默认不存控件类型**，而是按"字段语义"在生成期推断控件：

| 字段语义（来自实体字段元数据） | 默认显示 |
|------------------------------|----------|
| 文本（短） | `el-input` / 表格列文字 |
| 文本（长）/ 富文本 | `el-input textarea` / 详情 `v-html` |
| 数字 / 金额 | 数字格式化（千分位、两位小数） |
| 日期 / 时间 | `el-date-picker` / 格式化显示 |
| 开关（bool） | `el-switch` / 表格 `el-tag` |
| 下拉（字典） | `el-select`（options 来自数据源或字典服务） |
| 多选（字典） | `el-select multiple` |
| 树形（父级选择） | `el-tree-select` |
| 文件 / 图片（多） | 上传控件 / 多条下载链接 |
| 外键（关联实体） | `el-select` 远程搜索 / 显示关联名称 |
| 级联（多级） | `el-cascader` |

**映射规则与主链路（19 种控件映射）共用同一实现**，不许复制一套。
映射结果只作为默认值；用户在属性面板可显式覆盖控件类型，覆盖后生成器尊重覆盖值。

### 2.3 显示模板（用户自定义渲染的唯一通道）

不使用 Vue slot（Element 各组件 slot 支持不统一，且树结构上无法统一表达），
而是**存库的模板片段 + 生成期插入**：

- **容器级模板**：占位符 `items`（所有字段条目）、`item`（单个字段）。
  例：查询表单第 3 行插入自定义时间范围选择器 → 模板片段为
  `<el-date-picker type="datetimerange" ... />`，用 `item` 单条占位替换。
- **字段级模板**：占位符 `row.field`。
  例：订单号字段显示为可点击链接 →
  `<a @click="detail(row)">{{ row.orderNo }}</a>`。

模板片段存数据库表（`sys_page_display_template`，第一版可并入组件表模板字段），
生成期用 Marker 引擎（现有 `[gen.xxx]` 体系）按规则插入目标位置。
模板片段必须能被 Vue 模板编译器独立解析（每个片段是完整合法元素或 v-if 块），
生成后由构建验证兜底。

### 2.4 布局系统（el-row / el-col 统一渲染）

不做 WPF 式像素画布。布局 = 网格 + 预设：

- 预设表（用户选定后生成初始树，之后不再作为身份依据）：

| 预设 | 布局 |
|------|------|
| `blank` | 空容器 |
| `query-table` | 上方查询表单 + 下方表格 |
| `left-detail` | 左侧列表 + 右侧详情（1-1 栅格） |
| `master-detail` | 主表 + 子表 |
| `metrics-list` | 上方指标卡 + 下方列表 |

- 栅格规则：容器内字段用 `el-col :span`，`spans` 省略时自动 24/N；
  支持预设列数（1/2/3/4 列）与 1-2、1-2-1、2-1、2-1-2 等非等分布局。
- 树节点统一为 `Page -> el-row -> el-col -> container/data component`，
  响应式属性 `xs/sm/md/lg` 可选。
- 用户编辑只改树（AddRow/AddColumn/SplitColumn/SetGrid/Move/Wrap），
  保存时统一校验树与绑定。

## 3. 数据源绑定契约

组件不绑定模糊 DTO 名，而是绑定**已验证的数据源契约**：

```
service + method + dto + cardinality + parameters
```

| 基数（Cardinality） | 兼容容器 |
|--------------------|---------|
| `Collection / Paged` | table、子列表 |
| `Single` | edit-form、description |
| `Options / Collection` | 下拉、级联、远程选择 |
| `Aggregate` | 指标卡、统计展示 |

规则：

- 字段控件必须引用所属数据源中的有效 `FieldId`。
- `ParametersJson` 只能引用页面参数、路由参数、事件参数或其他数据源公开字段，生成前验证。
- 服务与方法必须来自 CodeMaster 已知的**实体能力目录**（由实体生成能力推导、只读输出），
  禁止填写任意方法名后直接生成调用代码（安全 + 权限边界）。
- 同一字段可在同一页面多次出现（查询表单一次、表格一次、详情一次），
  因此复杂页面节点身份用 `componentId / bindingId`，不用 `fieldId`。

### 3.1 视图数据源（SourceType = View）

视图是开发者通过**视图构建器**显式创建的数据库视图，或数据库中已存在的视图导入：

```
选择实体（多选）→ 勾选字段 → 配置外键（关系图仅作建议，可改）
  → 生成方言正确的 SELECT 初稿
  → 自由编辑任意 SQL（where/join/函数/子查询，不强制结构）
  → 声明只读实体字段（属性名 / SQL AS 别名 / C# 类型 / 键列）
  → CREATE VIEW（PG/Oracle/MySQL: OR REPLACE；SqlServer/Sqlite: DROP+CREATE）
  → 拉取视图实际列，与声明字段比对并给出非阻断提示
  → 生成只读实体（跳过 Add/Update/Delete；含 TenantId/DeptId 自动继承对应基类）
  → 生成只读服务（GetPageList/GetDetail/GetOptionList，复用实体服务生成器）
  → 自动注册为实体数据源，进能力目录，页面绑定照旧
```

要点：

- 字段勾选仅为生成 SQL 初稿的便利，不是约束；SQL 可以完全手写。
- 同一个表可以在手写 SQL 中使用多个 `AS` 实例；一对多、多表、聚合和计算表达式不由 CodeMaster 深度推理或禁止。
- 用户声明的属性名、SQL 输出列名和 C# 类型是代码生成元数据。CodeMaster 只检查重复名称、重复列映射、只读 SQL、键类型等确定性约束，不证明复杂 SQL 的唯一性或类型等价性。
- 数据库实际列仅用于创建后的差异提示；存在差异时仍按用户声明生成实体，运行或构建错误由真实数据库/编译器返回。未声明实体字段时才从数据库视图列推断。
- 权限语义按列名适配：含 `TenantId` → 租户过滤；含 `DeptId` → 数据权限；都没有 → 仅登录可读。
- SQL 只存在于开发者显式创建的视图定义中，**不提供运行时任意 SQL 查询接口**。
- 视图实体变化走现有 SchemaHash / NeedsSync 反向传播。

### 3.2 API 数据源（SourceType = Api）

API 数据源用于绑定当前运行项目中已经注册到 Dynamic API 能力目录的查询服务：

- 设计器只列出能力目录中的 `GET` 方法，不允许自由填写任意路由或方法名。
- 服务方法的 HTTP 路由、请求方式、返回 DTO、数据形态和路由参数都来自同一能力目录，
  页面定义保存和生成时会再次校验，避免前端配置与真实 Swagger 路由漂移。
- 当前版本支持最多一个路由参数，且参数必须位于路由末尾；该参数必须在 `ParamsJson`
  中使用结构化 `$ref` 显式提供，例如 `{"id":{"$ref":"$route.id"}}`。
- 当 API 返回 DTO 与现有实体 DTO 一致时，设计器自动关联该实体字段模型，可继续做字段级绑定；
  自定义聚合 DTO 暂时只支持容器级绑定，字段级结构化绑定留待 DTO 字段目录完善后开放。
- `SqlQuery` 仍只是枚举预留值，页面定义、生成器和 UI 都不得启用运行时任意 SQL。

API 数据源还支持导入外部 OpenAPI 3.x 契约。导入流程以文档为版本边界，先解析并展示
operation、请求/返回 DTO、字段和嵌套关系的变更，再由用户确认应用：

- `operationId` 是 API 数据源稳定身份；缺失时使用规范化的 `METHOD + route`。
- 每个对象 schema 映射为带 OpenAPI 绑定的 `MetadataOnly` 元数据实体，只保存契约和字段结构，不生成任何后台或 DTO 代码。
- 标量属性映射 `EntityField`；对象和对象数组保存在 OpenAPI 组合边中，不创建数据库外键关系。
- 重新导入采用已接受快照 + 当前元数据 + 新契约三方比较。新增、修改、疑似重命名、待删除和冲突
  必须先预览；删除只有显式确认后才执行，已被页面引用的字段、DTO 或 API 保留并标记冲突。
- 元数据实体不能进入实体服务、视图构建器、一对一或一对多关系，也不能执行常规代码、菜单或多语言生成；它只供 API 数据源和前端页面生成读取。
- `oneOf`/`anyOf` 等暂不能精确映射的结构保留完整契约 JSON，生成安全的 `object` 兜底并在预览中提示复核。

## 4. 设计器改造（数据源配置）

现状缺口：`entityDesigner` 属性面板只有通用 key-value 属性，**没有数据源一等公民**。

改造目标：属性面板新增"数据源"配置区：

- 页面级：统一通过“添加数据源”选择实体、注册视图或 API；管理服务 / 方法 / DTO / 基数 / 参数。
- 视图入口复用视图构建器，完成后以只读实体数据源加入当前页面，不在页面定义中保留独立 View 分支。
- API 入口从 Dynamic API 能力目录选择已注册 GET 方法，页面保存和生成共享同一契约校验。
- 容器级：选择绑定哪个数据源；容器内字段树自动列出该数据源字段。
- 字段级：显示字段语义推断出的默认控件 + 允许覆盖；可挂字段级显示模板。
- 容器级：可挂容器级显示模板（覆盖默认 items 渲染）。

数据源配置是**结构化 JSON（DB 规范表）**，不是字符串，保证 AI 可读写。

## 5. Agent 复杂页面工作流（AI 生成剧本）

AI（Codex 等）生成复杂页面的标准剧本，决策点必须输出理由：

```
1. 需求理解      读需求 → 列出页面要展示的实体数据、联动关系、是否只读/可编辑
2. 实体盘点      查项目实体 → 确认字段、关联、字典枚举
3. 数据形态决策   全部展示还是新建聚合 DTO？
                  决策点：字段来自多个实体/需要统计 → 新建 DTO（后端 +Swagger 生成）
                  单实体/字段够用 → 直接用实体 DTO（不改后端）
                  【必须输出理由】
4. 后端 API      实体服务缺方法（分页查询、下拉选项、按父 ID 查子列表）→ 补方法
5. Swagger 验证  调用 Swagger/API 确认 DTO 字段与形态（该平台已实现动态 API + Swagger）
6. 前端搭建      打开复杂页面设计器 → 选布局预设 → 建容器
7. 绑定          容器绑定数据源 → 字段自动映射控件 → 检查默认值 → 按需覆盖控件/挂显示模板
8. 验证          生成 → 目标项目构建 → 交互走查（查询/分页/详情/联动）
```

AI 平台能力清单（Agent 在此平台上可用的操作）：

- 读项目实体定义、字段、字典、关联（含 DB 表 `sys_*` 与 `tree.json`）。
- 调用代码生成服务生成/增量同步复杂页面。
- 写后端实体服务方法 + 调 Swagger 验证 DTO。
- 读写设计器结构化数据源/绑定配置（JSON 契约）。
- 触发目标项目真实构建验证（复用现有构建隔离环境）。

**关键原则**：AI 的规划结果必须先转换成结构化 DTO，通过项目边界、服务能力、
DTO 形态、字段、组件兼容性验证，再执行生成。不能让 AI 绕过生成器直接手写 Vue。

当前 Agent 接入由私有适配程序集动态贡献两个工具：读取复杂页面上下文、提交完整结构化
页面方案。方案中的每个数据源形态、显式控件覆盖和后端变化都必须带决策理由；API 变化还
必须带 Swagger 验证证据。审批通过后只产生“保存定义 → 生成页面 → 构建项目”动作。

## 6. 外部 Vue 重新导入

外部导入仅用于显式接纳目标项目中的模板修改，不会反向推断任意脚本逻辑：

1. 用 Jint 执行锁定版本的 `@vue/compiler-sfc@3.5.28` 官方 `parse()`。
2. 将 template AST 映射回现有 `Component` 模型，`tree.json` 格式不变。
3. 按 `data-gen-id` 重新绑定已有节点；没有稳定标识的节点标记 `Origin=External`。
4. 展示 Added/Changed/Removed 差异，用户确认后才写 tree。
5. 导入前备份完整 Vue、tree 和 page sidecar，并单独保存原始 `<script setup>` 内容。
6. 重新生成时外部节点随 tree 合并保留；脚本不做 AST 反向合并，必要时从备份人工恢复。

区域保护侧车为 `index.vue.genhash.json`，外部导入备份目录为
`.codemaster-backup/external/{timestamp}/`。

## 7. 与现有 Change / 主链路的关系

| 模块 | 归属 |
|------|------|
| 数据模型（ProjectPage/PageDataSource/PageComponentBinding/PageEntityDependency） | `complex-page-definition-and-binding`（已完成设计） |
| 布局树、增量同步、外部 Vue 重新导入 | 同上 |
| 容器模型（4 种）、字段语义映射、显示模板、设计器数据源面板 | 本工作流（`complex-page-container-ai-workflow`） |
| Agent 工作流剧本与能力清单 | 本工作流 |
| 传统 CRUD 生成（ModuleEntityService/TemplateCodeGenerator） | 不变，禁止破坏 |

实现顺序建议：

1. 先落容器模型与字段语义映射（无界面，纯生成层，可单测）。
2. 再落显示模板（Marker 引擎已有基础）。
3. 再改设计器属性面板（数据源配置区）。
4. 最后 Agent 工作流文档化并接入（AI 只调用前 3 步的接口）。

## 8. 未来展望：AI 更强之后，这个方案还有没有必要

**有，且会更重要。** 理由：

1. **方案的本质不是"模板"，而是"数据驱动契约"**。无论 AI 多强，它都需要一个
   可校验、可增量、可回滚的中间表示来落地界面；容器树 + 绑定 + 模板正是这个中间表示。
2. **AI 的价值在"决策"，本方案的价值在"执行安全"**。AI 负责需求分析、DTO 设计、
   控件选择；生成器负责把决策翻译成不会编译失败的 Vue，并在实体变化时增量更新。
3. **AI 越强，越需要约束**：无约束的 AI 直接写 Vue 会产生不可维护、互相冲突的代码。
   结构化契约让 AI 输出可审计、可复用、可测试。
4. **反向依赖**：未来"AI 根据需求直接生成复杂页面"的能力，正是建立在
   `complex-page-definition-and-binding` + 容器模型之上——先有契约，才有自动规划。

唯一可能弱化本方案的是：AI 直接生成并长期维护整个目标项目的 Vue 代码（替代生成器）。
即便如此，容器模型仍可作为 AI 的思维脚手架（思考的 DSL），只是落点从"生成器"变成"AI 直接产出"。
因此本方案的重心应放在**契约设计得足够自然、可读、可被 AI 直接消费**，
而不是依赖某个特定生成引擎。
